# SAT PDF -> CSV parser (v4)

Читает PDF с SAT-вариантами постранично, просит Gemini вытащить вопросы,
пишет три CSV (`ebrw_mcq.csv`, `math_mcq.csv`, `math_open.csv`) и заливает
кропы картинок в Supabase Storage.

## Установка

```bash
pip install -r requirements.txt
cp .env.example .env      # и вписать ключи
```

## Запуск

```bash
python sat_parser_gemini.py --folder ./pdfs --output ./out --resume
```

Полезные флаги:

| флаг | зачем |
|---|---|
| `--resume` | продолжить с места остановки (по батчам, не по файлам) |
| `--concurrency 3` | несколько батчей одновременно — быстрее, но быстрее и лимиты |
| `--batch auto` | по умолчанию: размер батча подбирается под каждый файл |
| `--batch 3 --overlap 1` | зафиксировать вручную: страниц в запросе / перекрытие |
| `--gap-rounds 3` | раундов добора пропущенных номеров |
| `--no-upload --images-dir ./img` | не трогать Supabase, кропы класть локально |
| `--dry-run` | прогон без заливки картинок |
| `--models a,b,c` | своя очередь моделей |
| `--limit 3 -v` | обработать 3 файла с подробным логом (удобно для проверки) |
| `--no-answer-keys` | не искать и не подставлять ответы из файлов-ключей |
| `--list-models` | показать ID моделей, доступных твоему ключу |
| `--no-rescue` | не перезапрашивать поодиночке страницы без вопросов |

## Разные форматы файлов

Файлы приходят непохожие: где-то один вопрос на лист, где-то шесть
скриншотов на странице. Подбирать флаги под каждый файл не нужно — скрипт
настраивается сам:

* **Размер батча.** Перед разбором файла смотрится первая страница с
  вопросами, и у модели отдельно спрашивается, сколько на ней блоков
  (считать ей легче, чем переписывать). Дальше батч берётся так, чтобы за
  запрос уходило примерно шесть вопросов: плотный лист — одна страница за
  запрос, редкий — до шести. В логе это строка
  `на странице примерно N вопрос(ов) -> батч M`. Зафиксировать вручную —
  `--batch 3`.
* **Размер модуля.** Берётся из напечатанного заголовка (`27 QUESTIONS`),
  а не из зашитых цифр. Поэтому подборка на 15 задач считается законченной,
  а не модулем с двенадцатью потерянными. Зашитые 27 и 22 применяются
  только когда файл действительно похож на полный тест.
* **Границы модулей.** Определяются по рестарту нумерации, а не по лейблу:
  в оригинальных файлах заголовок `Math Module 2` напечатан один раз и может
  стоять посреди страницы, а со всех остальных страниц модель вернёт `""`.

## Если вопросов вытаскивается мало

Главная причина — обрыв ответа по лимиту выходных токенов: модель перечисляет
вопросы, упирается в потолок и молча обрывается на середине. Скрипт это ловит
(`ответ обрезан по лимиту токенов, делю на N + M страниц`) и добирает остаток
меньшими батчами, вплоть до одной страницы за запрос.

Вторая причина — модель «ленится» и с групповой пачки возвращает вопросы
только с первой страницы. На этот случай два добора:

1. Страницы, с которых не пришло ни одного вопроса, перезапрашиваются
   поодиночке (`добор страниц без вопросов: N шт.`).
2. Дырки в нумерации. Вопросы в модуле пронумерованы подряд, поэтому
   пропущенный номер — доказательство пропажи. Такие номера запрашиваются
   прицельно, в несколько раундов, и каждый следующий раунд сужает окно
   страниц вплоть до одной (`добор по дыркам, раунд 2`).

Покрытие страниц и подобранный батч пишутся в `state.json`, так что при
`--resume` ничего не начинается заново.

Что ещё помогает на совсем мелком шрифте:

```bash
--dpi 250 --api-max-side 2400
```

Полезно сверять: в логе видно `+N вопросов` по каждому батчу, а в конце —
`осталось ненайденных номеров` со списком в `gaps_report.txt`. Пустой отчёт
означает, что нумерация в каждом модуле сплошная.

Первый прогон лучше делать так — видно, что получается, и не жжётся квота:

```bash
python sat_parser_gemini.py --folder ./pdfs --output ./test_out \
  --limit 1 --no-upload --images-dir ./test_out/img -v
```

## Раскладка PDF

Подпапки обходятся рекурсивно, `--folder` указывай на корень:

```
SAT Qs/
  June 2025/
    US Version A.pdf
    US Version A Answer Key.pdf
  March 2026/
    ...
```

* Период ищется сначала в имени файла, потом в именах папок снизу вверх.
  То есть `June 2025/US Version A.pdf` даёт период `June 2025` и версию
  `US Version A`, даже если в имени файла месяца нет.
* Колонка `source` — это путь относительно корня (`June 2025/US Version A`),
  поэтому одинаковые имена файлов в разных месяцах не считаются дубликатами.
* Ключ с ответами ищется сначала в той же папке, что и вариант, и только
  потом по всему дереву.

## Что важно знать

* **Ключи только в окружении/`.env`.** В коде их нет.
* **Файлы-ключи с ответами больше не выбрасываются.** Скрипт подбирает ключ
  к варианту по имени, читает его и подставляет `correct_answer` там, где на
  странице вопроса ответа не было. Подставляет только при однозначном
  совпадении по номеру (и модулю, если он распознан).
* **`has_image` и `image_url` — разные вещи.** `has_image=True` при пустом
  `image_url` = у вопроса есть рисунок, но кроп не получился. Это готовый
  список того, что стоит проверить руками.

## Картинки руками (`--manual-images`)

Координаты рисунка модель называет на глаз и промахивается в обе стороны:
у таблицы отрезает столбец, у графика захватывает половину текста вопроса.
Автоматический кроп это частично лечит (рамка раздвигается до белого поля),
но надёжным не становится.

С `--manual-images` скрипт ничего не режет, а составляет `images_todo.csv`:

| колонка | что в ней |
|---|---|
| `source`, `page` | в каком файле и на какой странице искать |
| `question_number`, `module` | какой это вопрос |
| `question` | начало текста вопроса, чтобы не перепутать |
| `file` | **под каким именем положить скрин** |

Имя файла проставляется в колонку `image_url` основного CSV сразу, ещё до
того как файл появится. То есть порядок такой: прогнал парсер → открыл
`images_todo.csv` → прошёл по страницам сверху вниз, сделал скрины → положил
их в `--images-dir` под указанными именами. Править CSV не нужно, ссылки уже
на месте. Папки под скрины (`ebrw_mcq/`, `math_mcq/`, `math_open/`) скрипт
создаёт заранее.
* **Прогресс** лежит в `state.json`, битые ответы модели — в
  `failed_batches_debug.log`.
* Если менять `--batch`/`--overlap` между запусками, недоделанные файлы
  перечитываются целиком (номера батчей уже не совпадают) — готовые файлы
  не трогаются.
* Колонки CSV изменились относительно v3 (добавились `module`,
  `question_number`, `page`). Дописывать v4 в старые CSV скрипт не станет —
  скажет об этом и попросит новый `--output`.

## Проверка без квоты

Рядом лежат тесты — они гоняют парсер на сгенерированных PDF с подставной
моделью. Реальный API не дёргается.

```bash
GEMINI_API_KEY=fake python3 test_gaps.py        # добор пропущенных номеров
GEMINI_API_KEY=fake python3 test_full_test.py   # полный тест на 98 вопросов
GEMINI_API_KEY=fake python3 test_layouts.py     # разная плотность страниц
GEMINI_API_KEY=fake python3 test_parser.py      # ротация моделей, resume, LaTeX
GEMINI_API_KEY=fake python3 test_resilience.py
```

`test_full_test.py` — главный: собирает файл из 98 вопросов (27 + 27 + 22 + 22)
с повторяющимися формулировками и заголовками модулей, как в оригинале, и
проверяет, что до CSV доехали все 98. Сначала с моделью, которая отдаёт всё
(так видно потери самого скрипта), потом с ленивой, которая отдаёт два вопроса
из трёх (так видно, что добор работает).
